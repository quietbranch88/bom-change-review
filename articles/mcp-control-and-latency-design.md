# 替料評估助手的 MCP 控制與多人使用設計

2026-10-04 初步設計筆記。後續已補上本機 SQLite 同步恢復及合成使用者的有限接案 demo；真實模型、HTTP 授權與多人模型效能仍待實作。最新狀態見[系統架構](../docs/architecture.md)與[驗證紀錄](../docs/verification.md)。下文保留初稿的設計思路。

做完 Neo4j 的資料設計，我接著想把模型接進來。

工程師可以直接問：「LM5155 這個候選現在還缺什麼？」或「為什麼這項檢查還不能判斷？」系統去找對應的案件、規格與來源，再把結果整理出來。這就是我想做的 AI 替料評估助手。

但想到這裡，我又有兩個問題。模型提出一個工具呼叫，系統是不是就照做？如果十個人同時問，大家會不會一直等？

所以這次我想先把模型、MCP 和控制流程一起設計好。這篇記錄的是初步設計；目前已有本機 MCP 與腳本模擬控制流程，真實模型接入和多人服務仍待實作，還沒有多人延遲的實測結果。

我希望延續前一篇的這句話：

> 判斷有依據、有規則；未知有原因，補齊有動作、有標準。

接上模型後，我們仍然要知道答案從哪裡來。多人一起用時，也要知道任務卡在哪裡、為什麼在等，以及什麼時候應該停止。

## 模型提出需求 程式負責執行

第一個要釐清的地方，是模型在流程裡負責什麼。

我希望模型理解使用者的問法，提出需要查哪些資料。系統再檢查它提出的工具和參數，通過後才執行，將結果交回模型。OpenRouter 官方的工具呼叫流程也區分了模型提出呼叫、應用程式執行工具，以及回傳工具結果這幾個步驟。[官方工具呼叫說明](https://openrouter.ai/docs/guides/features/tool-calling)

我們的流程可以先讀成：

**使用者問題 → 模型提出查詢 → 控制層檢查 → MCP 工具 → Neo4j 證據 → 核對結果 → 回答。**

控制層就是執行這段流程的程式。它管理允許的工具、案件版本、呼叫次數、時間和預算。模型提出要做的事，還需要通過這些檢查。

MCP 在這裡提供工具的標準接口，讓 client 能發現工具、知道參數格式並呼叫 server。第一版的工作是查詢，因此先做工具接口；文件內容或操作範本是否另外提供，要看之後的使用需求。[MCP 工具規範](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

如果問題永遠只有一種，而且每次都固定查同樣的資料，直接寫流程也能完成。我想用模型處理的是問法的差異，例如「查這次判斷的出處」和「接下來要找工程師補什麼」，分別需要哪些資訊。這個價值也需要測試，不能因為接上模型就假設它比較好用。

## 工具要先說清楚能做什麼

我先保留三個用途明確的工具：

| 工具用途 | 希望回答的問題 |
| --- | --- |
| 查候選規格 | 這個案件版本保存了哪些候選規格與條件 |
| 查案件缺項 | 目前缺什麼 下一步需要補什麼 |
| 查判斷依據 | 這次判斷實際採用了哪些規格和文件 |

它們都綁定同一個案件快照。快照代表當時採用的資料版本，讓我們可以回頭還原判斷依據。

如果模型換了一個案件 ID，或要求執行不在名單裡的工具，控制層就停止。查不到資料，也要明確回報，不能讓模型自己補成一個看起來合理的結果。

工具回傳不能只剩一句「符合」。我們需要保留判斷範圍、條件、來源、覆核狀態和缺項，才能知道這句話到底支持到哪裡。

例如 LM5155 的 BIAS 電壓規格有接法條件。如果案件沒有確認實際接法，下一步應該是取得設計資訊，不能讓模型自行挑一筆規格來比較。即使缺項補完，重新檢查也可能得到不符合；單項符合仍不能推論整顆料已經核准替換。

還有一個容易誤會的地方：工具標記唯讀，不代表已經有唯讀權限保證。MCP 的工具註記是提示；官方也明確說明，安全保證需要由實際控制落實。[官方工具註記說明](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)

目前專案有固定查詢與工具白名單，但資料庫帳號層級的唯讀隔離還沒有完成。這兩個狀態要分清楚。

## 多人使用要先分清楚任務與資源

再來是我比較在意的問題：如果很多人同時用，怎麼辦？

先要分清楚三件事。一個人在操作系統，不一定正在送出請求；一個已送出的任務，也不一定正在查資料庫。它可能正在等模型，或正在等前面的任務。

因此，我們需要分別限制進行中的任務、正在執行的模型請求，以及正在執行的資料庫查詢。

如果一個任務正在等模型，就不應該同時占著資料庫查詢名額。這些限制的目的，是讓各種資源在需要時才被使用，而不是把整段流程鎖成一條長隊。

目前本機 MCP server 在同一個程序內，一次只執行一個工具呼叫。這是現有的控制，不是多人共用服務的容量保證。假如開了四個程序，每個程序都有自己的限制，總量也會跟著改變。

初步多人版先採單一服務程序，統一管理有限的任務和等待隊列。隊列滿了就回報繁忙，不能無限收下去。某個人也不能一直占滿名額；第一版先限制每人一個尚未完成的任務。

這是我們的容量設計。MCP 的傳輸規範定義訊息如何送達；服務可以處理多少工作、怎麼排隊，還需要自己設計。[MCP 傳輸規範](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)

## 先量到慢在哪裡

當使用者說「很慢」，我希望系統能回答得更具體。

| 要量的時間 | 可以幫助我們看什麼 |
| --- | --- |
| 任務等待時間 | 工作進來的速度是否超過服務容量 |
| 每次模型請求時間 | 模型或供應商是否成為主要等待來源 |
| 工具等待與執行時間 | 工具是否排隊 或資料讀取是否慢 |
| 資料庫各次查詢時間 | 哪個固定查詢需要進一步檢查 |
| 驗證與呈現時間 | 回答整理是否增加了明顯延遲 |
| 使用者等待完整答案的時間 | 整段體驗到底花多久 |

模型內部也有不同階段。OpenRouter 文件區分了等待第一個 token 的時間，以及之後生成的速度。收到第一個 token，不表示答案已經生成並通過檢查。[官方延遲說明](https://openrouter.ai/docs/guides/best-practices/latency-and-performance)

第一版可以先顯示「等待處理」「查詢證據」等狀態，完成檢查後再顯示答案。這能讓人知道系統在做什麼，但不能拿畫面有更新就宣稱完整答案更快。

用一個假設理解排隊：十個任務一起進來，每個任務固定需要十秒，而且一次只能執行兩個。若全部接下來、都不取消，最後一批要到五十秒才完成。這只是忽略其他因素的排隊例子，不是本專案的效能測量。

所以我需要決定的不只是「一次開幾個」，還包括「最多讓多少人等」「等多久應停止」。

## 先減少重複工作 再評估增加容量

查現有程式時，我找到一個具體的重複工作。

目前三個 MCP 工具都透過同一個讀取器取得完整快照。對包含判斷資料的較新快照，一次讀取會查缺項、規格、判斷三次。如果三個工具各呼叫一次，程式路徑會執行九次資料庫查詢。這是讀取路徑推算，還沒有測到九次查詢花多久。

因此，第一個改善候選，是同一個任務共用一次已核對的快照讀取，再分別取得需要的規格、缺項和判斷依據。

這個設計預期可以減少重複查詢，實作後還要驗證答案相同、版本相同，並量完整任務的查詢數和耗時。不能先宣稱一定快了幾倍。

跨任務快取則需要更多考慮。假如不同人有不同權限，快取不能只用案件 ID 當 key；讀取之前仍然要確認這個人可以看這個案件。第一版先處理任務內重用，不急著加入共用快取。

## 多人一起花錢 預算也要一起管理

接模型還有費用問題。單一任務有上限，不代表整個服務就不會超支。

假如兩個任務同時看到「還有一筆預算」，都決定送出請求，就可能在帳單回來前已經承諾太多費用。初步設計是在送出前，先原子地保留這次請求的成本上界，再依實際用量結算。

「原子」在這裡的意思是：檢查剩餘預算與保留金額，是同一次不可被另一個任務插進來的決定。不能先各自查餘額，再各自扣。

估算要包含工具描述、問題、工具結果和輸出上限；模型若有另外計費的推理或請求費，也需要納入。費率或用量無法可靠確認時，應停止付費派送，不能用猜測取代上限。

OpenRouter 也有帳戶、金鑰及進行中請求的費用限制。不過我們仍需要管理這個服務自己的任務預算，並核對實際帳單。[官方費用與限流說明](https://openrouter.ai/docs/api/reference/limits)

逾時也不能直接視為沒有花錢。本機停止等待時，外部供應商可能仍在處理；結果未確認的保留金額，要等用量核對後再處理。

第一輪模型設計先限制最多兩次模型請求：一次提出查詢計畫，一次根據已取得證據選取回答引用。工具由程式執行，最多三次。這是待實作的新設計，不能把目前四次腳本規劃步驟，當成四次真實模型請求。

另外，我們要明確記錄供應商路由。應用程式不重試，不代表路由服務沒有嘗試其他供應商。OpenRouter 提供供應商選擇與關閉 fallback 的設定；第一版先固定符合參數要求的供應商路徑，以便核對結果與耗時。[官方路由說明](https://openrouter.ai/docs/guides/routing/provider-selection)

## 多人共用還需要案件權限

如果未來工程師 A 和工程師 B 查不同專案，就不只是延遲問題了。

知道案件 ID，不代表有權限讀取案件。服務需要從登入狀態取得可信任的身分，確認案件權限；MCP server 也要驗證可信任的呼叫身分，不能讓模型在參數裡自稱是某個人。

目前使用的是本機 stdio。多人共用 MCP service 時，我們規劃評估 Streamable HTTP 與對應的 HTTP 授權。這些是之後要實作和驗證的邊界，不是換傳輸就自動完成的功能。[MCP HTTP 授權規範](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

接上外部模型也表示資料會離開本機。第一版只使用公開案例和明確標示的合成情境；如果之後要使用內部 BOM 或設計文件，還需要決定哪些欄位可外送、供應商保留政策，以及資料如何刪除。這些產品決定不能由模型代替。

## 用可以驗收的情境檢查設計

我希望接好之後，先驗證這些情境：

- 不同問法能取得對應證據，並保留範圍與覆核狀態。
- 資料不足時，回答缺什麼與補齊標準；查不到或工具失敗時，明確停止。
- 模型提出非法工具、錯誤案件版本或不存在的引用時，被程式擋下。
- 多人同時提交時，任務、模型、資料庫與等待隊列都沒有超過設定上限。
- 權限不同的人不能讀到對方的案件，包括任務重用或未來快取的路徑。
- 模型慢、供應商限流或使用者取消時，能停止後續派送，並正確處理仍在進行的工作與費用。

效能測試則先測多人工作排程，再測真實 MCP 和 Neo4j，最後才做有預算限制的真實模型測量。用可控制延遲的假供應商，可以證明排隊和限制；它無法證明真實模型的速度。

測量時要記錄同時任務數、問題大小、模型和供應商、服務版本、CPU／RAM、暖機與重複次數。除了成功答案的 p50／p95，也要列出拒絕、逾時和失敗比例。不能把等太久而失敗的人排除後，就說服務很快。

現在我們有了可實作的設計，但真實模型、多人權限、容量控制和延遲測量還沒有完成。本機資料庫驗證也曾需要人工恢復啟動，冷啟動問題仍待處理，不能把恢復後的成功當成每次都能順利啟動。

這次我想學到的，是問清楚一個 AI 系統的責任：它取得什麼證據、可以執行哪些動作、同時能承接多少工作，以及做不下去時如何結束。把這些問題回答清楚，接模型和 MCP 才有可以驗收的設計。
