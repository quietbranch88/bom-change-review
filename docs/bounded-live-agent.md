# Authenticated Agent with bounded model requests

This optional workflow connects the existing SSO portal to a guarded planner and read-only OAuth HTTP MCP. The planner chooses evidence tools and fetched evidence bundles; the server binds their references and existing deterministic code renders the assessment and missing-data actions. It cannot approve a replacement, fabricate a specification, or expand the reader's case access.

The real Keycloak, portal HTTP action, MCP and Neo4j path has passed with a fixture model. Two separately approved real trials reached MCP evidence but rejected their final references. The [later in-app-browser trial](browser-live-verification.json) established that two of four mandatory references were missing; no answer was released. Successful live-answer and Chrome acceptance remain incomplete. The [implementation checkpoint](bounded-live-agent-verification.json) and [earlier application trial](live-model-trial-verification.json) preserve their original source bytes and narrower observations.

## Authentication before model work

The portal accepts only its server-owned session, exact case mapping, POST Origin and CSRF token. The application verifies the active resource token and matches issuer, subject, tenant, reader role and explicit snapshot grant before planner creation. That ordering prevents unauthorized requests from loading a model key, reserving funds, or sending data to the model. Permission is checked again before each model dispatch, around each evidence read and before disclosure. The MCP service independently enforces its own authorization checks.

The browser policy uses `Referrer-Policy: same-origin`, preserving the same-origin POST Origin while retaining exact Origin and CSRF checks. A `no-referrer` policy caused actual Chrome form submissions to send `Origin: null`, which the application correctly refused. See the [Fetch Origin algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header). Logout first ends the local session and revokes tokens, then redirects to a cookie-bound, expiring same-origin handoff. The user follows a fixed IdP sign-out link; no browser-provided redirect destination is accepted and `form-action 'self'` remains. The callback checks retained-token inactivity. This adds an explicit UI step; HTTP-only clients must follow the handoff link. In-app-browser and real HTTP checks cover this patch; Chrome remains incomplete.

Only an opaque session cookie reaches the browser. OAuth tokens go only from the BFF to the configured MCP resource, never into the model payload. The optional model receives a fixed synthetic question, snapshot identifier and bounded evidence summaries. Technical documents, questions and model output are untrusted. Exact-one function response, duplicate-key rejection, allowlisted tool names, snapshot binding and required citation checks remain local guards.

The two functions are `plan_evidence` and `finish_evidence`. The first selects two or three allowlisted read tools, including assessment and gaps. The second selects already-fetched bundles through `evidence_tools`; the model does not generate reference identifiers. Assessment status and next actions come from the evidence controller, not model prose. This is an intentionally constrained demonstration, not unrestricted autonomous reasoning. See [OpenRouter tool calling](https://openrouter.ai/docs/guides/features/tool-calling).

## Live transport and budget

The live mode requires both trusted `--agent-mode live` configuration and explicit `--allow-paid`. A generic browser click, question, environment key, or fixture launch cannot enable it. Before an approved trial, run the read-only check:

```sh
uv run --frozen --extra mcp python scripts/live_agent_preflight.py
```

The dedicated key is read from the local user environment setting `BOM_REVIEW_OPENROUTER_API_KEY`, never from a URL, form or public configuration. Do not paste it into chat, logs, screenshots or GitHub. The preflight checks the current model/provider endpoint and capped, non-resetting key; it does not create or change keys or send an inference request.

The adapter pins `mistralai/ministral-3b-2512` and `mistral/zdr`, disables fallback and plugins, denies provider data collection, requests ZDR, uses a25-second HTTP timeout, caps requests at20000bytes and responses at64KiB, and limits output to2048tokens. These are requested controls and local guards, not an independent audit of provider retention. The endpoint does not advertise `parallel_tool_calls`, so that wire field is omitted and multiple returned calls are rejected locally. This endpoint's unsupported `uniqueItems` is removed only from the provider schema; local duplicate rejection remains.

The reservation uses the endpoint's full context token price plus maximum output and10%headroom, rounded upward to micro-USD. At the observed endpoint prices it is0.014644USD per admitted attempt, against a0.02USD ledger. Settlement releases only the unused amount, so a sufficiently inexpensive first response can leave enough for the second reservation. If not, the second call is refused. Two durable admissions are the ceiling across cooperating processes and readers using the same trusted account/file, including uncertain outcomes. This is not multi-host coordination or a throughput guarantee.

OpenRouter reports usage cost in [USD-denominated credits](https://openrouter.ai/support); the adapter rounds reported costs upward to the existing ledger's micro-USD precision. Missing/invalid cost, transport error, cancellation or timeout retains the hold and blocks further work. Observed overrun is recorded and blocks subsequent requests; it is not described as a prevented bill. Reported BYOK usage is unknown exposure because external invoices are outside this quote. Wrong-model output is rejected while preserving a reported charge. No automatic retry, reconciliation, account rotation or ledger reset is implemented. See [usage accounting](https://openrouter.ai/docs/cookbook/administration/usage-accounting) and [key credit limits](https://openrouter.ai/docs/api_reference/limits).

The local ledger cannot guarantee that a provider bill never exceeds its reservation. A valid capped key, current pricing and explicit trial authorization are prerequisites, not evidence that actual inference succeeded. Provider request attempts and returned credit costs are not equivalent to settled external invoices. The portal's status endpoint deliberately does not report a fabricated zero-paid-call counter in live mode.

## Retention and limits

Only synthetic accounts and cases are in scope. Model sharing occurs only in explicitly enabled live mode. The BFF keeps OAuth tokens in bounded process memory and removes sessions at expiry/logout; private realm files, keys in the local user environment, trial SQLite files and local test logs are retained until an explicitly checked cleanup. No public raw provider-response archive is added by this workflow. Sanitized receipts describe results and source bytes, not credentials or account metadata.

Loopback HTTP, experimental Keycloak resource indicators, static grants, single-process portal state and database administrator credentials behind fixed read queries remain demo limitations. Corporate federation, production TLS, global distributed admission, image advisories, stable model quality, EDA simulation and hardware approval are not established. The HTTP harness substitutes localhost Secure-cookie policy and does not prove Chrome behavior.
